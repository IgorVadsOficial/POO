Relacionamentos & Conceitos UML Aplicados

Todos os conceitos exigidos para a defesa oral explicados com mini-SVGs fiéis ao Diagrama EX03.png.

1. Composição (Losango Preenchido)

Todo-Parte Forte

Onde aparece: Voo (1) ◆── (0..*) Reserva.
Significado: Relação todo-parte forte com dependência de ciclo de vida. Uma reserva pertence a um único voo e não faz sentido existir se o voo for removido.

2. Agregação (Losango Vazio)

Todo-Parte Fraca

Onde aparece: Em dois pontos do diagrama: (1) Voo ◇── "É tripulado por" ── Aeroviario (o tripulante continua existindo após o voo e pode tripular vários voos) e (2) Passageiro ◇── Reserva (o passageiro agrupa suas reservas como todo-parte independente).

3. Generalização / Herança

Relação "É um"

Linha contínua + triângulo vazio (──▷): Tanto Operador quanto Aeroviario apontam para <<abstract>> Funcionario, herdando nome e getNome() e aplicando polimorfismo em getCargo().

4. Associação Simples (Linha Reta)

Sem Seta / Sem Losango

Linha contínua simples (──): Usada em três ligações do diagrama: Reserva ── Operador (0..* e 0..1) e nas duas ligações paralelas entre Voo e Aeroporto diferenciadas pelos nomes "Parte de" e "Chega em".

5. Implementação / Realização

Conceito Comparativo

Linha tracejada + triângulo vazio (- -▷): Não está no diagrama porque não usamos interface. Como Aeroviario e Operador herdam estado (- nome) e comportamento (+ getNome()), a modelagem correta é Generalização de Classe Abstrata.

6. Navegabilidade (Diagrama vs Código)

Bidirecional no Desenho

No Diagrama EX03: Nenhuma associação possui ponta de seta aberta (──>). Na UML, associações sem seta indicam navegabilidade não restrita (bidirecional no modelo conceitual).
Na Implementação (EX04.py): A navegabilidade foi materializada pelos atributos privados de referência:

  • Bidirecional no código: Passageiro ↔ Reserva, Voo ↔ Reserva e Operador ↔ Reserva (ambos guardam referência mútua).
  • Unidirecional no código: Voo → Aeroporto (__partida, __destino) e Voo → Aeroviario (__tripulantes).

7. Multiplicidade & Cardinalidade no Diagrama EX03

Notações presentes: 1 (exatamente um) • 0..1 (zero ou um / opcional) • 0..* (zero ou muitos).

Ligação no Diagrama EX03 Multiplicidades Interpretação Semântica
Voo ◆── Reserva 1 (Voo) e 0..* (Reserva) Um Voo compõe de zero a muitas Reservas; toda Reserva pertence obrigatoriamente a exatamente 1 Voo.
Reserva ── Operador 0..* (Reserva) e 0..1 (Operador) Um Operador gerencia de zero a muitas Reservas; uma Reserva pode ter 0 ou 1 Operador (pois o passageiro pode reservar sozinho).
Passageiro ◇── Reserva 1 e 0..* (nota de leitura) Semanticamente, 1 Passageiro possui 0..* Reservas (conforme o losango vazio em Passageiro e o atributo - reservas : Reserva[]). Dica de defesa: no desenho, os rótulos 0..* e 1 ficaram trocados nas pontas da linha vertical — se o professor notar, basta explicar que o losango vazio está corretamente em Passageiro (o todo) e cada reserva pertence a 1 passageiro.
Voo ◇── Aeroviario / Voo ── Aeroporto Implícitas pelos atributos No desenho, estas linhas usam rótulos textuais ("É tripulado por", "Parte de", "Chega em") sem números na linha, mas a multiplicidade está explícita nos atributos de Voo: tripulantes : Aeroviario[] (muitos) e partida / destino : Aeroporto (1 cada).

from abc import ABC, abstractmethod


class Aeroporto:
    def __init__(self, nome, cidade, pais, capacidade):
        self.__nome = nome
        self.__cidade = cidade
        self.__pais = pais
        self.__capacidade = capacidade

    def getPais(self):
        return self.__pais


class Funcionario(ABC):
    def __init__(self, nome):
        self.__nome = nome

    def getNome(self):
        return self.__nome

    @abstractmethod
    def getCargo(self):
        pass


class Aeroviario(Funcionario):
    def __init__(self, nome, funcao):
        super().__init__(nome)
        self.__funcao = funcao

    def getFuncao(self):
        return self.__funcao

    def getCargo(self):
        return self.__funcao


class Voo:
    def __init__(self, codigo, horario, data, partida, destino, assentos):
        self.__codigo = codigo
        self.__horario = horario
        self.__data = data
        self.__partida = partida
        self.__destino = destino
        self.__assentos = assentos
        self.__reservas = []
        self.__tripulantes = []

    def assentosLivres(self):
        return self.__assentos - len(self.__reservas)

    def getTripulacao(self):
        return self.__tripulantes

    def getTipo(self):
        if self.__partida.getPais() == self.__destino.getPais():
            return "NACIONAL"
        else:
            return "INTERNACIONAL"

    def getReservas(self):
        return self.__reservas


class Reserva:
    def __init__(self, codigo, passageiro, voo, operador):
        self.__codigo = codigo
        self.__paga = False
        self.__passageiro = passageiro
        self.__voo = voo
        self.__operador = operador

    def getCodigo(self):
        return self.__codigo

    def getPaga(self):
        return self.__paga

    def setPaga(self, paga):
        self.__paga = paga

    def getVoo(self):
        return self.__voo


class Passageiro:
    def __init__(self, nome, cpf):
        self.__nome = nome
        self.__cpf = cpf
        self.__reservas = []

    def criarReserva(self, voo, operador=None):
        if voo.assentosLivres() == 0:
            return None
        reserva = Reserva("R" + str(len(self.__reservas) + 1), self, voo, operador)
        voo.getReservas().append(reserva)
        self.__reservas.append(reserva)
        return reserva

    def cancelarReserva(self, reserva):
        reserva.getVoo().getReservas().remove(reserva)
        self.__reservas.remove(reserva)

    def pagarReserva(self, reserva):
        reserva.setPaga(True)

    def getReservas(self):
        return self.__reservas


class Operador(Funcionario):
    def __init__(self, nome, matricula):
        super().__init__(nome)
        self.__matricula = matricula
        self.__reservas = []

    def criarReserva(self, passageiro, voo):
        reserva = passageiro.criarReserva(voo, self)
        if reserva:
            self.__reservas.append(reserva)
        return reserva

    def cancelarReserva(self, passageiro, reserva):
        passageiro.cancelarReserva(reserva)
        if reserva in self.__reservas:
            self.__reservas.remove(reserva)

    def getCargo(self):
        return "Operador"


natal = Aeroporto("Aeroporto de Natal", "Natal", "Brasil", 20)
lisboa = Aeroporto("Humberto Delgado", "Lisboa", "Portugal", 40)

voo = Voo("AD100", "08:00", "20/12/2026", natal, lisboa, 2)

    for i, r in enumerate(passageiro.getReservas(), 1):
        print(i, "-", r.getCodigo(), "| paga:", r.getPaga())
    return passageiro.getReservas()[int(input("Qual reserva? ")) - 1]


while True:
    print("\nVoo", voo.getTipo(), "| assentos livres:", voo.assentosLivres())
    print("1 Reservar | 2 Cancelar | 3 Pagar | 4 Tripulação | 0 Sair")
    opcao = input("> ")

    if opcao == "1":
        if perfil == "1":
            reserva = passageiro.criarReserva(voo)
        else:
            reserva = operador.criarReserva(passageiro, voo)
        print("Reservado!" if reserva else "Voo cheio.")

    elif opcao == "2":
        reserva = escolher_reserva()
        if perfil == "1":
            passageiro.cancelarReserva(reserva)
        else:

    elif opcao == "3":

Bloco 2 — Classe Abstrata Funcionario e Subclasse Aeroviario 
class Funcionario(ABC):
    def __init__(self, nome):
        self.__nome = nome

    def getNome(self):
        return self.__nome

    @abstractmethod
    def getCargo(self):
        pass


class Aeroviario(Funcionario):
    def __init__(self, nome, funcao):
        super().__init__(nome)
        self.__funcao = funcao

    def getFuncao(self):
        return self.__funcao

    def getCargo(self):
        return self.__funcao

Abstração & Herança: Funcionario não pode ser instanciada diretamente. Aeroviario herda de Funcionario e invoca super().__init__(nome).

Polimorfismo: getCargo() é sobrescrito em Aeroviario retornando self.__funcao (ex: "Piloto"), enquanto em Operador retorna "Operador".

class Operador(Funcionario):
    def __init__(self, nome, matricula):
        super().__init__(nome)
        self.__matricula = matricula
        self.__reservas = []

    def criarReserva(self, passageiro, voo):

        if reserva:

    def getCargo(self):
        return "Operador"

Delegação & Reuso (DRY): Operador.criarReserva() delega a operação para passageiro.criarReserva(voo, self), centralizando a verificação de assentos livres e mantendo as listas de Voo, Passageiro e Operador sempre sincronizadas.

Separação de Responsabilidades: Apenas Passageiro possui pagarReserva().

"A partir de Voo, conectamos a classe Aeroporto por meio de duas associações simples paralelas, sem setas de navegabilidade — portanto conceitualmente bidirecionais no diagrama — diferenciadas pelos papéis 'Parte de' e 'Chega em'. Na classe Aeroporto, além de nome, cidade e capacidade de decolagens por hora, incluímos o atributo privado país e o método público getPais(), permitindo que o próprio Voo deduza automaticamente se é nacional ou internacional comparando os países de origem e destino."

"Nos relacionamentos todo-parte, aplicamos com rigor a diferença entre Composição e Agregação. Entre Voo e Reserva utilizamos Composição — indicada pelo losango preenchido encostado em Voo — com multiplicidade 1 para 0..*, pois existe dependência forte de ciclo de vida: uma reserva só existe vinculada a um voo específico. Já entre Voo e Aeroviario utilizamos Agregação — losango vazio encostado em Voo com o rótulo 'É tripulado por' — porque o aeroviário possui ciclo de vida independente: ele continua sendo funcionário da empresa após o voo e pode tripular vários voos. Da mesma forma, modelamos Passageiro agregando Reserva com losango vazio, pois o passageiro agrupa suas reservas sem que elas definam sua existência."

"Para os funcionários da companhia, aplicamos Generalização (herança) — representada pela linha contínua com triângulo vazio — partindo das subclasses Operador e Aeroviario para a superclasse Funcionario. Marcamos Funcionario com o estereótipo <<abstract>> e o nome em itálico porque ela não deve ser instanciada diretamente. Optamos por uma classe abstrata via generalização em vez de uma interface (implementação) porque as subclasses compartilham estado (nome) e comportamento concreto (getNome()), além do método polimórfico getCargo()."

"Por fim, fechando as regras de negócio: Passageiro possui os métodos para criar, cancelar e pagar reservas, enquanto Operador possui apenas criar e cancelar reservas, ligando-se a Reserva por uma associação simples com multiplicidade 0..* no lado de Reserva e 0..1 no lado de Operador — refletindo que uma reserva pode ser feita tanto com o auxílio de um operador (1) quanto diretamente pelo passageiro sozinho (0)."
